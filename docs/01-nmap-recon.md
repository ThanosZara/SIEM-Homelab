# TCP SYN Port Scan Detection
## Scenario Overview

An Nmap TCP SYN scan (ports 1–30) was run from a Kali VM against the pfSense gateway in an isolated VirtualBox lab. Snort detected the scan pattern with a threshold-based rule, the Splunk Universal Forwarder shipped the alerts to Splunk, and a scheduled Splunk alert flagged any source probing 10 or more distinct ports.

- **MITRE ATT&CK** | Discovery: [T1046 Network Service Discovery](https://attack.mitre.org/techniques/T1046/)
- **Attacker (Kali Linux):** `172.30.2.108`
- **Target (pfSense Gateway):** `172.30.2.1`
- **Sensor(Snort on Ubuntu Server):** `172.30.2.110`
- **SIEM(Splunk Enterprise on Linux Mint):** `172.30.2.104`
- **Detection sources**: Snort alert file (primary), pfSense firewall logs (cross-validation)

## Execution

The stealth port scan was executed from Kali Linux targeting the ports 1-30 of the gateway :

`sudo nmap -sS -p 1-30 172.30.2.1`

<img width="502" height="218" alt="εικόνα" src="https://github.com/user-attachments/assets/796eb2ca-20d3-4865-a999-0f0cd8a14fee" />

We can see that Port `22/tcp` (SSH) was **open**. Ports 1–21 and 23–30 were reported **filtered**. The gateway answered the SYN with a **SYN/ACK**, which means a service is listening on port 22., but no response from the other ports.

## Detection: Snort

##### Snort Rule:

`alert tcp any any -> $HOME_NET any (msg:"Nmap Scan - TCP SYN"; flags:S; detection_filter:track by_src, count 10, seconds 5; classtype:attempted-recon; sid:1000001; rev:2;)` 

**Why a threshold?** The reason I added a threshold (`detection_filter:track by_src, count 10, seconds 5`) is to make sure that it would fire only when a single source sends 10 SYNs within 5 seconds, which reduces the number of false positives. The drawback is that  `detection_filter` begins alerting only after the threshold is crossed, so the first 10 probes of the scan aren't logged.

##### Alerts Triggered:

Once the threshold is reached, alerts begin and display the attacker's source IP and port.

<img width="1286" height="346" alt="εικόνα" src="https://github.com/user-attachments/assets/af4d9d74-36f1-481a-99af-5983568b27a9" />

Snort wrote the alerts in fast-log format to `/var/log/snort/snort.alert.fast`, where the **Splunk Universal Forwarder (UF)** monitors this file and forwards it to Splunk over **TCP 9997**. I created the `inputs.conf` file on the Snort VM (`/opt/splunkforwarder/etc/system/local/inputs.conf`) to monitor this file path, assign the `snort` sourcetype, and direct the data to the `main` index .

## How I would triage this alert

1. **Confirm it's real:** check the Snort alert lines and the pfSense logs for the same source and window. Two sources agreeing means it isn't a parsing artifact.
2. **Identify the source:** is `172.30.2.108` a known host, such as an authorized vulnerability scanner? If not, it's unexpected reconnaissance.
3. **Check what was reached:** which ports answered? Here, only SSH on the gateway.
4. **Look for follow-up:** did the same source then attempt SSH logins or connect to other hosts? A scan alone is low severity; a scan followed by login attempts is not.
5. **Decide:** document and monitor, or escalate and block the source.

## Troubleshooting log

Problems encountered while building the detection and how each was diagnosed. 
#### 1. Every Alert Counted Twice
- **Symptom:** A 30-port scan produced 100 events and every per-port count was even (2 or 4).
- **Root Cause:** Snort alerts were still reaching Splunk over syslog (I had set up the Universal Forwarder because I believed syslog wasn't delivering). Two rsyslog rules on the Snort VM forwarded all messages (`*.*`) to Splunk: line 54 of `/etc/rsyslog.conf` and line 49 of `/etc/rsyslog.d/50-default.conf`, so each alert arrived twice.
- **Resolution:** Commented out both rules and `output alert_syslog` in `snort.conf`, and kept the Universal Forwarder as the only route. A fresh scan produced 50 separate alerts.
#### 2. A Full Scan Appeared as 2 Events

<img width="1135" height="644" alt="εικόνα" src="https://github.com/user-attachments/assets/6361a73a-ab5b-44ca-aeab-6c462fddf2a5" />

- **Symptom:** A search over a 30-port scan returned 2 events with `... lines omitted ...` inside, so `stats count` returned 2 and `rex` extracted only the first match per event.
- **Root Cause:** Splunk had no line-breaking rules for the new file-based source, so it merged consecutive alert lines into single events.
- **Resolution:** Defined the sourcetype in `props.conf` on the Splunk server (`SHOULD_LINEMERGE = false`, a `LINE_BREAKER: ([\r\n]+)` and restarted Splunk. The next scan indexed as 50 separate events.

#### 3. Splunk VM Ran out of Disk Space

- **Symptom:** Splunk showed a low disk space warning and stopped indexing new events, so searches stopped returning recent data. `df -h` on the Splunk VM showed the root partition almost full.
- **Root Cause:** The Splunk VM's virtual disk was too small(only 25GB) for the OS, Splunk Enterprise and the indexed data from three log sources. Splunk pauses indexing when free disk space falls below its minimum threshold, which is why data stopped arriving.
- **Resolution:** Shut down the VM and increased the virtual disk in VirtualBox (File → Tools → Virtual Media Manager, or `VBoxManage modifymedium disk <file> --resize <MB>`). Inside the guest, extended the partition with GParted and grew the filesystem, then confirmed the new size with `df -h` and restarted Splunk. Indexing resumed and the data gap closed once the forwarders caught up.
